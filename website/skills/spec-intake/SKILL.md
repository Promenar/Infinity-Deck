# 需求收敛

把模糊的开发请求整理成一份可直接交给实施计划的规格。本技能只负责需求、约束和验收标准，不写实施步骤。

## 何时使用

满足任一条件时，在规划或编码之前使用：

- 用户要求新功能、重构、工作流、界面、接口、迁移或架构调整，但具体行为没有说清。
- 工作要拆给多人或多个代理，需要一份共同的契约。
- 没有明确的验收标准，成功与否全凭主观判断。
- 可能存在非目标、兼容性要求、数据或安全边界。
- 用户的措辞是“大概”“类似”“参考”“优化一下”“重构一下”“做成某种效果”，或以其它方式留下了关键行为未定。
- 用户要求拷问、深挖或压力测试一个方案或设计：按下文“访谈轮次”的完整模式进行，直到决策树没有未决分支。

不适用：很小且明确的修改、直接执行命令、纯事实查询，或用户已经给出完整规格、只需要实施计划。

## 收敛流程

1. **先读现有材料**：工作区中的 README、已有规格或设计文档、相关源码与配置。用 `list_files`、`search_files`、`read_file` 查找；目录型工作区根部的 `AGENTS.md`、`CLAUDE.md` 已由应用作为项目规则提供，无需重复读取。
2. **区分事实与假设**：从仓库、文档、运行结果或用户陈述中核实的内容记为事实；其余明确标为假设，不藏在计划里。
3. **用访谈轮次解决待定决策**：只有当错误假设会改变用户可见行为、数据结构、安全姿态、成本或不可逆操作时才问用户；其余作为标注过的假设继续推进。
4. **产出规格**：按下文“规格结构”输出，可以直接交给实施计划或分工。
5. **保存位置**：同一轮就开始实施时，规格留在对话中；项目已有规格目录或用户要求保存时，再写入文件。

## 访谈轮次

提问方式参考 mattpocock/skills 的 grilling（MIT），按决策树逐轮推进：

- 把待定事项整理成决策树：每个决策下面挂着依赖它的后续决策。每一轮只问“前提已经确定、现在就能回答”的那一批问题，不替用户预设尚未回答的上游选择。
- 每个问题附推荐答案和一句理由，措辞让用户回答“是”即采纳推荐；用户只需对不同意的项给出修改。
- 能从仓库、文档、运行结果或网络一手资料查到的事实由自己查（文件工具、`web_search`、`web_fetch`），不问用户。
- 问题聚焦可观察的行为、取舍、优先级、成本与风险，不问实现细节；必须涉及技术选型时，先用一句话说明对用户可见的差别。
- 默认快速模式：阻塞决策少时一轮结束，其余写入“假设”。用户要求拷问、深挖，或需求涉及多个模块时进入完整模式，逐轮推进直到决策树没有未决分支，并在开始实施前请用户确认已达成共识。
- 完整模式下可以用 `update_plan` 记录已决与未决的决策节点。
- 每轮格式：

```markdown
❓ **Q1 <问题标题>**：<问题与可选项>
➡️ 推荐：<推荐答案>（<理由>）
```

## 规格结构

默认使用以下结构：

```markdown
# <功能 / 改动> 规格

## 目标
一两句话描述要达到的结果。

## 现有事实
- 从仓库、文档、界面、日志或用户陈述中核实的事实。

## 假设
- 用户不纠正时将采用的假设。

## 非目标
- 明确排除的行为与范围。

## 用户可见行为
- 主流程、边界情况、错误、空状态、权限与兼容性预期。

## 验收标准
- 可测试的检查项，写成用户不读代码也能确认的可观察结果（命令输出、页面表现、截图或产物）。

## 约束
- 技术、安全、隐私、性能、设计、平台、依赖与迁移约束。

## 风险与未决问题
- 会影响规划或分工的风险。

## 后续入口
- 建议的下一步：实施计划、分工执行、测试先行、直接小改，或继续向用户澄清。
```

## 交接规则

- 规格足以实施时，交给多步实施计划（可用 `update_plan` 列出步骤）。
- 工作可以并行或分工时，交接规格并写明各部分的文件或职责边界。
- 行为变化需要测试时，明确写出测试先行的入口。
- 访谈后仍有未决决策时，停下来问用户，不自行编造业务规则。

## 常见错误

- 把实施计划写进规格：规格止于需求、约束与验收标准。
- 只因为规格有用就创建项目治理文件。
- 隐藏不确定性：使用“假设”与“未决问题”栏目。
- 让执行实施的一方自行补齐产品决策：规格由主导者负责。
- 没有项目约定或用户要求时就把规格存成文件。
