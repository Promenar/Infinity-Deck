# 代码评审

目标是找出会导致错误行为、安全风险或维护负担的问题，并给出能直接执行的修改建议。先找真问题，再谈风格。

## 1. 确定范围

- 评审对象：对话中粘贴的代码、工作区文件、一组改动（diff）或整个目录。
- 读代码用文件工具：
  - `list_files` 了解目录结构，`search_files` 查找函数定义、调用点和配置；
  - `read_file` 读取文件，长文件用 offset/limit 或行号范围分段读；
  - `diff_file` 查看文件的变更。工作区是 git 仓库时，可以用 `shell_exec` 运行 `git status`、`git diff`、`git log -p -1` 获取改动（需要用户审批）。
- 确认背景（能从代码或说明判断的不必问）：语言与框架版本、这段代码的用途、改动意图、运行环境（服务器、移动端、浏览器、脚本）、评审重点。
- 只评审要求的范围；为理解行为可以读调用方和被调用方，但范围外的问题单独列为“附带发现”。

## 2. 阅读方法

1. 先读入口和公开接口，弄清输入、输出和副作用。
2. 跟踪主要数据流：数据从哪里来、经过哪些转换、写到哪里。
3. 对每个分支问“这个条件为假会怎样”“这个值为空会怎样”。
4. 对改动评审时，同时看改动前后的行为，确认调用方是否都已适配。
5. 有测试时读测试，判断测试覆盖了哪些情况、遗漏了哪些。

## 3. 检查清单

### 正确性
- 逻辑是否实现了声明的意图；条件、比较运算符、取反是否写反。
- 差一错误：循环边界、切片区间、分页偏移、日期区间的开闭。
- 类型与单位：整数除法、浮点比较、溢出、时区、货币精度、字符编码。
- 状态：初始化、重置、缓存失效、全局可变状态。
- 返回值是否被检查；异步结果是否被等待。

### 边界与错误处理
- 空值、空集合、空字符串、零、负数、超大输入、重复元素。
- 外部输入（用户输入、文件、网络响应）的格式校验。
- 异常是否被吞掉；错误信息是否足以定位；失败时资源是否释放（文件、连接、锁）。
- 重试是否有上限和退避；部分失败时数据是否一致。

### 并发
- 共享可变状态是否加锁或使用线程安全结构；锁的范围和顺序（死锁）。
- 先检查后执行（check-then-act）的竞态；读改写是否原子。
- 异步任务的取消、超时与生命周期；回调在哪个线程执行。
- UI 线程上的阻塞调用（网络、磁盘、数据库）。

### 安全
- 注入：SQL、命令行、路径拼接、模板、正则（ReDoS）。
- 鉴权与授权：每个入口是否检查身份与权限；越权访问其它用户数据。
- 敏感信息：密钥、令牌硬编码；日志或错误信息泄露个人数据。
- 不可信数据的反序列化、文件上传、路径穿越、SSRF、XSS。
- 加密：自研加密、弱算法、固定 IV、随机数不安全。
- 依赖：引入的新依赖是否必要、版本是否固定。

### 性能
- 循环内的数据库或网络调用（N+1）；可以批量的操作逐条执行。
- 算法复杂度与数据规模不匹配；不必要的全量加载、复制或排序。
- 缓存缺失或无上限增长；资源泄漏（监听器、定时器、连接）。
- 只指出有实际影响的性能问题，并说明在什么数据规模下会出现。

### 可读性与可维护性
- 命名是否准确表达含义；函数是否只做一件事。
- 重复代码、过深嵌套、魔法数字。
- 注释是否与代码一致；公共接口是否有必要的文档。
- 与项目现有约定（目录结构、错误处理方式、日志风格）是否一致。

### 测试
- 改动的行为是否有测试覆盖；修复缺陷是否有回归测试。
- 测试是否断言了有意义的结果，而不是只验证“没有抛异常”。
- 边界情况和错误路径是否覆盖；测试之间是否相互依赖。

## 4. 严重度

| 等级 | 含义 | 示例 |
| --- | --- | --- |
| 严重 | 会导致数据丢失、安全漏洞、崩溃或主流程错误，必须修改 | SQL 注入；空指针导致启动崩溃 |
| 重要 | 特定条件下行为错误或明显性能问题，合并前应修改 | 分页最后一页丢数据；循环内查询 |
| 建议 | 可维护性、可读性问题，不影响当前行为 | 函数过长；命名含糊 |
| 细节 | 风格与格式，可选 | 多余空行 |

只有能说清触发条件和后果的问题才标“严重”或“重要”。不确定是否为问题时，写成提问并说明需要确认什么。

## 5. 输出格式

```markdown
## 评审结论
<一两句话：整体判断，是否可以合并，最需要处理的问题>

## 问题列表
### [严重] <问题标题>
- 位置：`src/order/service.py:42-48`
- 问题：<发生了什么，触发条件>
- 影响：<后果>
- 建议：<具体改法，必要时附代码片段>

### [重要] ...

## 附带发现
- <范围外但值得注意的问题>

## 做得好的地方
- <值得保留的做法，一两条即可>
```

- 问题按严重度排序，同级按文件顺序。
- 位置写到文件和行号（以 `read_file` 输出的行号为准）；粘贴代码没有行号时引用函数名和关键代码行。
- 建议给出具体修改，不写“注意处理异常”这类泛泛的话。
- 没有发现某类问题时不必逐项罗列“无”。

## 6. 修改代码

评审默认只读。用户要求修复时：

1. 先列出准备修改的问题清单，按用户确认的范围修改。
2. 用 `read_file` 获取当前内容后，用 `patch_file` 按行修改，或用 `write_file` 写入；每次修改后重新读取确认结果。
3. 能运行测试时（`shell_exec` 或 `python_exec`，需要用户审批），修改后运行相关测试并报告结果；无法运行时说明未验证。

## 7. 自查

- 每个“严重”“重要”问题都写清了触发条件，并在代码中核对过，不是凭模式匹配猜测。
- 位置准确，用户能直接跳转。
- 没有把个人风格偏好标成高严重度。
- 评审范围与用户要求一致。
