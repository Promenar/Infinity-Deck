# 内置模型网关规划

> 日期：2026-11-10
> 状态：规划稿，待用户决定第 8 节的问题；尚未进入实现
> 范围：Infinity Deck 应用侧的账号、充值、余额、用量能力，以及与自建 NEWAPI 的对接方式

## 1. 目标与非目标

### 目标

- 新用户不需要自己申请任何服务商的 Key：注册一个 Infinity 账号即可开始对话。
- 应用内原生完成注册、登录、余额查看、充值、用量查看、账号资料与注销。
- 内置网关以“内置服务商”的形式进入现有服务商体系，聊天、工具调用、模型目录沿用现有链路。
- 用户自带 Key 的全部能力保持可用，两种方式可以并存。
- 网关成为后期盈利点之一。

### 非目标

- 自研网关后端。后端使用自建部署的 NEWAPI，应用只调用它的 HTTP 接口。
- 修改 NEWAPI 源码。需要的行为优先用它的后台配置实现。
- 在本规划阶段确定具体价格数字、上游模型供应合同和运营主体。

## 2. 调查结论

### 2.1 应用现状

以下路径省略前缀 `native-ui/app/src/main/java/com/promenar/infinity/`。

可以直接复用：

| 密钥存储 | `data/security/SecretStore.kt`、`AndroidKeystoreSecretStore.kt`、`SecretCatalog.kt` | Keystore 加 AES-GCM；按 ID 存取；备份时加密导出 |
| 服务商保存入口 | `data/manager/ProviderManager.kt`、`navigation/ProviderConfigurationSave.kt` | 新增、更新、凭据写入 |

| 用量专区框架 | `ui/settings/TokenUsageScreen.kt`、`TokenUsageViewModel.kt` | 按模型、会话、每日聚合 |

必须新增：

- **内置服务商标识**。现有数据模型（`data/model/ProviderModels.kt`）没有“内置”或“只读”字段，删除入口也不区分。需要固定 ID、地址与协议只读、删除改为退出登录。
- **账号体系**。应用内目前没有任何账号、登录态或会话代码，只有 GitHub 设备码和 Tailscale 两处第三方登录。
- **NEWAPI 账号接口客户端**。注册、登录、刷新、令牌、余额、充值、用量。
- **支付跳转与回跳**。应用没有 Custom Tabs 依赖，清单里没有任何 http/https 或自定义 scheme 的深链。
- **服务端余额与真实扣费**。现有费用是客户端价格表（`data/model/ModelSpecs.kt:1808`）估算的美元数，没有任何地方读取服务端余额。
- **402 映射**。HTTP 402 目前在正文没有关键词时会被归为“请求无效”。
- **首启引导分支**。`ui/welcome/OnboardingProviderStep.kt` 现在要求填地址和 Key。

### 2.2 NEWAPI 现状

核实版本：`QuantumNous/new-api` 的 `v1.0.0-rc.49`，2026-11-08 发布，是 GitHub 标记的最新发行版。以下均来自该标签的源码与仓库内 `docs/authentication.md`。

- **许可证**：AGPL-3.0，另有 NOTICE 附加条款：修改版必须在界面保留 “Frontend design and development by New API contributors.” 署名和指向原项目的可见链接。改系统名、Logo、页脚可用后台配置完成，不需要改代码。
- **鉴权**：登录返回 15 分钟有效的 Access Token（JWT，`Authorization: Bearer`），Refresh Token 只通过 `new_api_refresh` Cookie 下发，最长 30 天，每次刷新轮换。另可创建带权限范围的个人访问令牌（`nap_` 前缀）。
- **注册**：用户名、密码、邮箱、邮箱验证码。不支持手机号与短信。第三方登录支持 GitHub、Discord、OIDC、LinuxDO、Telegram、微信和自定义 OAuth。
- **人机验证**：只有 Cloudflare Turnstile。开启后注册、登录、发验证码、重置密码都要带 token；原生端要用 WebView 取 token。
- **重置密码**：邮件链接指向网页控制台，新密码由服务端生成，用户不能自设。
- **额度**：500000 额度等于 1 美元；展示货币与汇率由后台配置并经 `/api/status` 下发。
- **充值**：兑换码、易支付、Stripe、Creem、Waffo、Waffo Pancake。没有微信支付或支付宝官方商户直连，也没有 App 支付 SDK 下单。在线支付都是“下单返回链接，外部页面支付，服务端回调入账”。
- **支付合规开关**：管理员必须先在后台确认支付合规条款，否则在线支付、兑换码、订阅、邀请返利全部禁用。
- **订阅套餐**：有。套餐带价格、时长、额度、重置周期，购买后可把用户切到指定分组，到期回退。分组决定可用模型和价格倍率。
- **赠送**：新用户赠送额度、邀请双方赠送额度、每日签到，默认都是 0 或关闭。
- **用量**：日志、统计、按时间聚合接口齐全。`/api/pricing` 下发模型倍率、按次价格、分组可用性、供应商与标签。
- **注销**：`DELETE /api/user/self` 存在，需要先做二次验证。
- **风控**：邮箱域名白名单、邮箱别名限制、按 IP 的关键接口限流（默认 20 次 / 20 分钟）、按分组的模型请求限流、令牌级额度与 IP 白名单、敏感词。没有设备级风控和全局 IP 黑名单。

尚未核验：登录二次验证接口的请求体字段、`quota_type` 取值含义、注销后日志与充值记录是否清除。这三项在第 7 节阶段 0 的接口冒烟里确认。

### 2.3 Google Play 支付政策

来源为 Play Console 帮助中心的 Payments 政策及其问答（answer 9858738、10281818、15582165、13821247、10144311）。

- 在 Play 分发的应用内销售数字商品必须使用 Play 结算，官方例子包含虚拟货币和订阅。模型额度属于此类。
- 应用不得把用户引向其它支付方式，范围包括应用内的按钮、链接、WebView 和注册流程。
- **消费型应用是合规做法**：应用内不提供购买、不放通往支付的链接，用户在别处购买后在应用内登录使用。可以用不带链接的文字说明。
- 美国自 2025-10-29 起不再强制 Play 结算，但需要加入替代结算或外部链接计划、上报交易并缴纳服务费；欧洲经济区、韩国、印度等各有地区计划。
- 应用内可以创建账号的，必须提供应用内注销入口和网页注销入口。

## 3. 总体方案

### 3.1 两类凭据，两条通道

| 通道 | 凭据 | 用途 |
|---|---|---|
| 对话通道 | `sk-` 模型令牌 | `/v1/chat/completions`、`/v1/models` 等。作为内置服务商的 API Key 存入 `SecretStore`，走现有协议层，不改聊天链路 |
| 账号通道 | Access Token 加 Refresh Cookie | `/api/user/*`、`/api/token/*`、`/api/log/*` 等账号接口，由新增的网关账号客户端使用 |

登录成功后，应用自动创建或复用一个名为设备名的 `sk-` 令牌，取回完整值存入钥匙串。用户看不到也不需要理解这个令牌。

Refresh Cookie 存入 `SecretStore`，Access Token 只放内存，遇到过期自动刷新。刷新失败时把内置服务商标为“需要重新登录”，不影响其它服务商。

服务端在反向代理后会校验刷新请求的 `Origin`，原生端需要在刷新和退出请求上带服务端配置的可信地址。

### 3.2 内置服务商

- 固定 ID（例如 `builtin_gateway`），名称用品牌名，地址由构建配置注入（参照 `GITHUB_OAUTH_CLIENT_ID` 的做法），协议固定为 OpenAI 兼容。
- 服务商列表里置顶显示，展示登录状态和余额；点进去是账户页而不是地址与 Key 表单。
- 未登录时不出现在模型选择器里。
- 现有的“主服务商”位置规则不变：谁先配置谁是主服务商。

### 3.3 模型下发

- 可用模型：登录后用 `sk-` 令牌请求 `/v1/models`，沿用现有同步逻辑。
- 能力与上下文：沿用内置目录和 `newapi/` 前缀识别。
- 价格：从 `/api/pricing` 读取，仅用于内置网关的模型，在模型页展示。其它服务商继续使用客户端价格表。
- 默认启用：现有逻辑下新拉到的模型默认不启用。内置网关的模型改为默认启用，默认模型取运营侧指定的推荐模型。推荐清单放在已有的签名目录发布站（`promenar.github.io/Infinity-Deck/model-catalog/`）里，不依赖 NEWAPI 的字段。

### 3.4 渠道差异

| 能力 | 侧载版 | Play 版 |
|---|---|---|
| 注册、登录、注销 | 有 | 有 |
| 余额、用量 | 有 | 有 |
| 兑换码 | 有 | 待定（见 8.3） |
| 在线充值 | 应用内下单，用 Custom Tabs 打开支付页，回到应用后轮询到账 | 没有购买入口，没有支付链接 |
| 订阅 | 有 | 没有购买入口，只展示状态 |

用 `DistributionCapabilities` 新增一个开关，充值相关界面放进 `sideload` 源集，Play 包里不包含这些代码和字符串。

## 4. 用户流程

### 4.1 新用户首启

1. 引导的服务商步骤顶部出现“用 Infinity 账号开始”，下方保留现有“使用自己的 Key”宫格。
2. 选择账号路径：输入邮箱，收验证码，设密码，完成注册并自动登录。
3. 应用在后台创建模型令牌、拉取模型、启用推荐模型并设为默认。
4. 直接进入首聊。新用户赠送额度足够完成首聊与若干次试用。

### 4.2 余额不足

1. 对话返回额度不足，气泡下的失败提示给出“充值”按钮（Play 版给出“查看余额”）。
2. 进入充值页，选金额和支付方式，在浏览器页签里完成支付。
3. 回到应用，充值页自动轮询到账并刷新余额，用户重试上一条消息。

### 4.3 已有用户

- 设置的服务商列表里出现内置网关入口，未登录状态显示“登录”。
- 登录后内置网关的模型进入模型选择器，与自带 Key 的模型并列，不改变现有默认模型。

### 4.4 换机与恢复

- 新设备上登录同一账号即可，应用为新设备创建新的模型令牌。
- 从备份恢复时，如果备份包含密钥，模型令牌随之恢复；登录态需要重新登录。

### 4.5 注销

- 账户页提供“注销账号”，先验证密码，再调用注销接口，随后清除本机的登录态和模型令牌。
- 另备一个网页注销入口，供 Play 上架材料填写。

## 8. 待用户决定的问题与建议

### 8.1 账号体系

NEWAPI 只支持邮箱，不支持手机号。

建议：邮箱加密码，注册必须过邮箱验证码。第三方登录先不做，后续按需要加 GitHub 或 OIDC。手机号登录需要改 NEWAPI 源码或在它前面加一层自己的账号服务，与“不自研后端”的前提冲突，不建议在首版引入。

连带问题：找回密码的后半段在网页完成，且新密码由服务端生成。建议首版接受这个体验，在应用里提示“查收邮件”。

### 8.2 登录态与令牌保存

建议：Refresh Cookie 与模型令牌都存入现有 `SecretStore`；Access Token 只放内存。模型令牌按现有服务商密钥的规则进入加密备份。Refresh Cookie 每次刷新都会轮换，恢复出来的旧值大概率已失效，建议不进入备份，恢复后重新登录。

这与“备份覆盖钥匙串全部内容，仅排除自动备份口令”的既有目标有出入，需要确认是否为它开一个例外。

### 8.3 充值与支付

侧载版建议分两步：先上兑换码，再上在线支付。在线支付渠道取决于目标用户：

- 面向大陆用户：NEWAPI 只有易支付聚合通道可接微信和支付宝，没有官方商户直连。易支付通道的资质参差，资金和合规风险由运营方承担。
- 面向海外用户：Stripe 或 Creem，需要境外主体或对应的收款资质。

Play 版建议做成消费型：应用内没有购买入口和支付链接，只能登录、看余额和用量。用户在官网或侧载版充值。

需要决定：Play 版是否保留兑换码入口。政策没有明确写兑换码，但“在应用外购买、在应用内兑换数字额度”有被认定为绕过 Play 结算的风险。建议 Play 版不放兑换码入口。

接入 Play 结算是另一条路：NEWAPI 没有 Play 结算回调，需要自建一个校验购买凭证并调用 NEWAPI 管理接口加额度的小服务，且要付 Play 的服务费。建议等网关跑出真实付费数据后再评估。

### 8.4 定价与会员权益

建议首版只做预付费钱包：按量扣费，统一在上游成本上加一个倍率。订阅套餐放到阶段 6，用 NEWAPI 的套餐加分组实现“每月额度加更低倍率或更多模型”。

需要决定：展示货币用人民币还是美元；加价倍率；是否做充值档位折扣。

### 8.5 新用户赠送额度

建议：赠送一个小额度，够完成首聊和十几轮对话，必须过邮箱验证才发放，并开启邮箱别名限制。免费额度只能用低成本模型，用单独的分组实现。邀请奖励和签到首版不开。

需要决定：具体金额，以及是否限制免费额度可用的模型。

### 8.6 模型列表下发

建议按 3.3 执行：可用模型取 `/v1/models`，价格取 `/api/pricing`，推荐与默认模型放在已有的签名目录发布站。

需要决定：首批上架哪些模型，这同时决定上游供应和合规范围。

### 8.7 与自带 Key 的并存和默认引导

建议：两者完全并存。新用户引导里账号路径在上、自带 Key 在下，两条路都保留。已有用户不弹任何打扰，只在服务商列表里多一个入口。内置网关不抢占已有用户的默认模型。

### 8.8 隐私与合规

这是全案里最需要先定的一项，它决定账号体系、支付渠道和部署位置。以下只列事实，不构成法律意见。

- 面向大陆公众提供生成式 AI 服务，涉及《生成式人工智能服务管理暂行办法》下的备案或登记、真实身份信息、ICP 许可或备案、未成年人消费限制；用户内容发往境外模型涉及个人信息出境规则。
- NEWAPI 没有手机号实名，README 明确要求运营方自行完成这些合规事项。
- 应用需要补充用户协议、隐私政策，并在 Play 的 Data safety 中申报账号与邮箱的收集。

建议：首版定位为小范围试运营，以兑换码方式发放给已有用户，不做公开的大陆收款；同时确定运营主体和目标市场，再决定在线支付渠道。未成年人方面，在用户协议里设定年龄门槛，注册时勾选确认。

需要决定：运营主体在哪里；首要市场是大陆还是海外；是否提供大陆已备案的国产模型与境外模型两条线路。

### 8.9 风控与滥用防护

建议首版配置：注册必须邮箱验证，开启邮箱别名限制，按分组设置模型请求限流，免费分组用更严的限流，赠送额度保持小额，每个设备一个模型令牌并设置额度上限。

Turnstile 会让注册登录多一步网页验证。建议首版不开，观察到批量注册后再开，并在应用里用 WebView 取 token。

NEWAPI 没有设备级风控。如果出现规模化薅取赠送额度的情况，下一步是在网关前加一层校验设备完整性的小服务，这属于后续评估项。

### 8.10 域名与部署位置

建议：用 `infinityware.work` 下的子域名，账号接口和模型接口同域，Cloudflare 在前。应用内的地址由构建配置注入，验证环境和正式环境可以切换。

部署位置取决于 8.8：面向海外或试运营阶段，建议放在到上游模型和到大陆用户延迟都可接受的地区；面向大陆公开运营需要境内主机和备案。

需要决定：子域名名称；部署地区；数据库与 Redis 的托管方式；谁负责 NEWAPI 的升级和备份。

### 8.11 开源许可证

NEWAPI 是 AGPL-3.0 并带署名附加条款。不改源码、只做部署和后台配置时，需要保留网页控制台上的署名和原项目链接。应用只通过 HTTP 调用它，应用自身是否受 AGPL 约束属于法律判断，建议在公开运营前请专业人士确认。

建议：不改 NEWAPI 源码；确需定制的逻辑放在独立的旁路小服务里。

## 9. 风险

- **NEWAPI 版本不稳定**。最新发行版是 rc，鉴权刚重构。用固定版本和接口冒烟脚本控制。
- **支付渠道**。大陆收款只有聚合通道，这是商业化的主要不确定项。
- **Play 审核**。消费型形态要求 Play 包里完全没有购买入口和通往支付的链接，包括帮助页和账户页里的跳转。
- **密钥安全**。模型令牌在设备上，设备被攻破等于余额可被消耗。用令牌级额度上限和设备会话管理降低损失。
- **成本敞口**。赠送额度与上游价格波动会直接变成成本，需要运营侧的监控与告警。
